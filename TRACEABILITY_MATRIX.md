# ClearFlow Dental Clinic — Requirement-to-Evidence Traceability Matrix
**Version:** 0.1 — initial cross-batch matrix  
**Prepared:** 2026-10-27  
**Scope:** Research batches B17–B36; dental SaaS on a tenant-isolated backend; India/Telangana applicability remains a separate review.  
**Status:** Working matrix, not a frozen schema or a legal/clinical compliance opinion.

## Purpose and reading rules

This matrix links source observations to candidate ClearFlow requirements and testable acceptance conditions. It is a traceability artifact—not a claim that every field has been exhaustively enumerated. Detailed evidence remains in the linked source-specific addenda and PROJECT_NOTES.md.

Evidence labels:
- **Observed** — explicitly documented in a cited source or reviewed database/API behavior.
- **Candidate** — an architectural or product requirement inferred from the evidence and project safety principles.
- **Pending** — requires additional source review, clinical validation, legal review, or an explicit product decision.
- **Not universal** — the source is a comparator, not an authoritative requirement for every clinic or for India.

Priority labels:
- **P0** — security, patient safety, integrity, or irreversible-data risk.
- **P1** — necessary for reliable clinical operations and traceability.
- **P2** — important coverage or interoperability enhancement; sequencing depends on product scope.

## Next consolidation pass

1. Extract a field-level inventory from each source-specific addendum and label each item as observed source field, candidate canonical concept, display-only value, derived value, or legal/clinical policy.
2. Map source table/API field → candidate entity/field → transformation/mapping → lifecycle events → role/tenant boundary → acceptance test.
3. Review each P0 row against the actual repository implementation and automated tests. Do not mark a requirement “implemented” based on documentation alone.
4. Perform a targeted official-source update for all India-specific legal and standards claims; the B35 notes are leads, not final legal conclusions.
5. Ask clinical reviewers to validate tooth numbering, periodontal measurement semantics, specialty chart data and prescription workflows before locking the model.
6. Only after gaps are reviewed should the matrix be used to generate an implementation schema or API contract.

**Decision:** Matrix v0.1 is an initial cross-batch scaffold. It does not assert full field coverage, legal compliance, clinical completeness or deployment readiness. Simplify interaction and presentation, not the evidence model.
