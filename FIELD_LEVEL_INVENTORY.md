# ClearFlow Dental Clinic — Field-Level Domain Inventory
**Version:** 0.1 · **Reviewed:** 2026-10-27 · **Purpose:** Source-to-candidate mapping before schema design  
**State:** A structured inventory of fields and data groups found in Batches 17–37. It is not a frozen schema, a complete clinical terminology set, or a legal compliance declaration.

## How to interpret this file

- **Observed source field/concept** means present in the cited system/documentation; it does not mean the same field is required for all clinics.
- **ClearFlow candidate** means retained, normalized, or added to meet traceability, safety, lifecycle or interoperability needs. It must be validated.
- **Source-specific** means a vendor enum, storage encoding, unit, field name or workflow that should be preserved as source data and mapped rather than copied as the global canonical field.
- **Conditional / scope pending** means only collected/activated where clinically justified, authorized, in the product scope or required by the applicable jurisdiction.
- **Not yet exhaustive** means cross-batch fields are summarized by groups. The detailed source addenda remain the source-by-source evidence ledger.

Every field group intended for implementation should ultimately have type, unit, null/missingness meaning, cardinality, relationship/tenant boundary, constraints/default, provenance, lifecycle, retention, display rule, API/write rule and acceptance test.

## 1. Present application schema — verified on backup branch

The app preserved on `backup/before-project-notes-reset-2026-10-27` contains only three TablesDB tables in the live `clearflow_dental` database. The following is the current structural baseline, not a recommendation for the future canonical model.

| Table / source column | Current Appwrite shape | Observed implementation use | Limitation to trace |
|---|---|---|---|
| `dental_clinics.clinic_name` | Required string, max 255 | Workspace display label | No facility address, legal identity, category, registration/validity, timezone or credential registry |
| `dental_clinics.owner_user_id` | Required string, max 36 | Owner lookup, row permission owner | A raw string; no native relationship to user/tenant authority. Clinic owner is not the same as a flexible member/role table |
| `dental_patients.clinic_id` | Required string, max 36 | Client list filter and visit context | Raw string, no database-native relationship/integrity to clinic |
| `dental_patients.owner_user_id` | Required string, max 36 | Client filter and row permission identity | Single owner-centric model; no clinic team/membership/access grant |
| `dental_patients.full_name` | Required string, max 255 | Display and client search | No separate name history, local/pronounced name, identifier type/source, duplicate/merge events |
| `dental_patients.phone` | Optional string, max 64 | Display/search | One phone slot; no contact point type, verification, preference, effective date, do-not-contact, source |
| `dental_patients.notes` | Optional text | Basic free-text note | No author, timestamp, encounter link, sensitivity, final/signature/version or correction lifecycle |
| `dental_visits.clinic_id` | Required string, max 36 | Client query filter | Raw string; no native tenant relationship validation |
| `dental_visits.owner_user_id` | Required string, max 36 | Client query filter and row permission owner | Repeated owner field can disagree with linked clinic/patient unless checked |
| `dental_visits.patient_id` | Required string, max 36 | Client association to selected patient | Plain string; no relation constraint or cross-tenant parent validation in the browser code |
| `dental_visits.treatment_name` | Required string, max 255 | Visit title | Free text, not procedure catalogue/code/target/status |
| `dental_visits.treatment_date` | Required string, max 10 | Treatment calendar/date | Date-only string; no timezone/precision distinction, entry time or source/time context |
| `dental_visits.doctor_advice` | Optional text | Visit notes/advice | No author/provider, status, encounter type, signature/version/amendment or review/communication events |
| `dental_visits.next_visit_date` | Optional string, max 10 | Recommended follow-up date | Not a booking; no recall-type rule/version, reminder, appointment, patient response or completed follow-up |

**Observed platform metadata:** Row security is enabled on all three tables; table-level permission is `create("users")`; current row permissions in browser-created records grant the specific user read/update/delete. Indexes are present on owner, clinic and patient columns as recorded in Appwrite. The schema has no dental specialty, prescription, observation, inventory, order/result, imaging, signature, financial or message tables. This is only metadata inspection; no patient rows were read or changed.

## 10. Cross-field invariants to preserve through normalization

1. **Unknown is not negative:** unknown, not asked, patient denies, not applicable, unmapped and cleared/resolved differ where clinically important.
2. **Source and normalized values coexist:** retain raw source string/code/unit/status/time and the mapping rule/version; never silently coerce vendor sentinel values such as -1 into a clinical numeric measurement.
3. **Four clocks remain distinct:** effective/observed time, recorded/entry time, imported/source time and display/sort time; include timezone/precision where relevant.
4. **A statement is not an event of a different authority:** medication statement ≠ prescription ≠ dispense ≠ administration ≠ adherence; appointment ≠ encounter ≠ completed procedure; result received ≠ clinician reviewed; lab received ≠ quality-approved; reminder delivered ≠ care completed.
5. **Issued or signed artifacts are version-bound:** preserve the exact content/hash, issuer/signer/authority/time and amendment chain.
6. **Tenant-scoped relationship validation:** validate tenant ownership of every relation at every write and background-job boundary; client filters aren't a security boundary.
7. **Ledger state is derived:** stock and financial balances are projections of idempotent authoritative movements, not freely editable totals.
8. **Policy changes are effective-dated:** reference catalog, due-rule, fee/benefit, signature, retention, legal obligation and FHIR mapping versions do not retroactively mutate historic decisions.
9. **Sensitive and optional fields are purpose-limited:** existence in a US/vendor schema does not justify collecting the field for an Indian dental clinic.
10. **Every normalized concept must point to evidence or a decision owner:** unknown and unresolved source items stay visible rather than guessed.

## 13. Coverage limitations / completion gate
- B17–B38 research is summarized here by entity family. This is not yet a source-to-target row for every physical field in every vendor table/API. The next expansion should mine exact field names, type/nullable/enum/relationship/constraint behavior from each source addendum and original documentation, avoiding invented canonical fields.
- Direct Open Dental LabCases/Laboratories API field extraction remains unverified. Product/material/shade candidates must not be called confirmed vendor schema fields.
- India-specific legal status and clinic applicability require counsel/regulatory owner sign-off. Current NDC public notices M-2749 and M-2662 are included in B37 with testable product requirements.
- The actual app is currently a small three-table prototype on the preserved backup branch, not an implementation of this entire inventory. See IMPLEMENTATION_GAP_REVIEW.md; no production-readiness claim is made.
- A canonical schema proposal may be created only after field coverage, clinical validation, legal review, import/interop mapping, and P0 security tests are reviewed by named owners.

**Decision:** The inventory is a working field coverage register, not the final canonical schema. Preserve the whole justified domain model; make the interface simpler.
