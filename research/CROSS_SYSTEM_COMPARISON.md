# ClearFlow Dental Clinic — Cross-System Domain Comparison
**Version:** 0.1 · **Review date:** 2026-10-27  
**Purpose:** Compare what each reviewed source contributes to the candidate ClearFlow domain model, including lifecycle differences and prototype gaps. This is a comparison of evidence coverage, not a scorecard treating every source as a universal standard.

## Evidence conventions
- DentalPin: source-model/service/test observations for a modular dental ERP, including AI approvals, payments/refunds, inventory, periodontics, orthodontics, recalls, media and imports.
- Open Dental: first-party API/database-reference/manual evidence, particularly dental charting, procedure/plan, coverage/claims, prescriptions, recall, imaging, orthodontics and lab workflow.
- OpenEMR: first-party EHI Export table dictionary for patient/EHR, prescription, medication stock, orders/results, billing, audit/signature and messaging. It includes legacy and jurisdiction-specific data.
- ABDM/NRCeS FHIR: India health-information exchange profiles/care-context/consent flows, not a complete practice-management implementation.
- India official sources: NDC/EDRB notices, Telangana Gazette, DPDP commencement/Rules, CDSCO, AERB, biomedical-waste sources, a dental-clinic minimum-standards template and CBIC.
- ClearFlow prototype: preserved Vue/Appwrite code and live schema metadata reviewed read-only; not a full implementation of these domains.

“Explicit” means documented source fields or behavior. “Partial” means a related subset exists but not end-to-end lifecycle. “Exchange only” means the source defines a data exchange contract, not the operational workflow. “Absent” means not present in the inspected ClearFlow prototype. A source may still be incomplete for a domain even if the general product is mature.

## 2. What the comparison implies

1. DentalPin contributes modular transactional patterns and tests for tenant scoping, approval gates, idempotency, immutable financial records, stock movements, clinical snapshots, outbox and imports. Source code patterns are not proof every path is safe.
2. Open Dental is the strongest reviewed reference for dental charting, procedure/plan, periodontal measurements, insurance/claims/recalls/imaging/orthodontics and lab workflow. Many sources are API docs rather than full DDL; lab schema remains unverified.
3. OpenEMR EHI is broad and useful for discovery of patient, medication/prescription, orders/results, observation, billing, audit and signature fields, but includes US-specific fields, legacy encodings and imperial units.
4. ABDM/FHIR defines exchange profiles, care contexts and consent flow. It is not a replacement for the internal dental practice workflow.
5. India official sources add legal/operational constraints, not an entire software data model. Applicability depends on facility, professional, device, medicine, state and service scope.
6. ClearFlow's current prototype is far smaller: three tables for clinic, patient and visit. The reviewed browser code writes linked IDs directly; trusted server-side relationship validation and two-tenant runtime behavior remain unverified.

## 3. Design rules derived from this comparison

- Keep the canonical domain model independent from any one vendor; use versioned source adapters and lossless import/export maps.
- Label each field as source-observed, ClearFlow candidate, derived/projection, jurisdiction/policy-specific, or sensitive/conditional.
- Preserve raw source value + normalized value + mapping rule/version; retain unknown/unmapped data without guessing.
- Keep adjacent lifecycle concepts separate even when a conversational action connects them: appointment vs encounter vs service; treatment plan vs performed treatment; medication statement vs prescription vs dispensing/adherence; order vs result vs clinician review; lab receipt vs quality approval; message delivery vs care completion.
- Enforce tenant relationships and action permissions in trusted backend code; UI filters aren't a security boundary.
- Choose MVP scope explicitly. Excluding payroll, insurance, lab, inventory, or imaging from the first release is acceptable if recorded as a scope decision, not silent field/domain loss.
