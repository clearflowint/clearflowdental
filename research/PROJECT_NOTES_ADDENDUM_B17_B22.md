# ClearFlow Dental Clinic — Research Addendum (Batches 17–22)

Updated 2026-10-27. Source-backed observations and design implications; not a final schema. Companion to PROJECT_NOTES.md.

## Batch 17 — AI operation execution, imports and tenant-safe relations
Sources: https://github.com/abinauv/dental-erp/blob/main/app/api/ai/command/route.ts ; https://github.com/abinauv/dental-erp/blob/main/app/api/ai/chat/route.ts ; https://github.com/abinauv/dental-erp/blob/main/lib/ai/command-executors.ts ; import upload/validate/commit routes under https://github.com/abinauv/dental-erp/tree/main/app/api/data-import
- The intent prompt tells the model to set requiresApproval=true for create_invoice/record_payment, but reviewed command route executes the action before returning that flag. Chat route also executes recognized actions before the answer. Model metadata is not an approval gate; server policy must stop unapproved execution.
- Invoice executor uses JavaScript Number, hardcodes 9% CGST+9% SGST, count+1 numbering and no explicit transaction wrapping unbilled treatments plus invoice lines in the inspected path. Payment creates receipt then separately updates invoice paid/balance/status without explicit transaction/idempotency. Stock update and stock transaction are separate writes. These are observed source-path risks, not claims about every route.
- Partial-name/phone matching can return first record; any write target needs stable IDs and disambiguation. Import accepts age and DOB together and can invent '.' as missing surname; import invoice may accept paid/balance summary. Preserve source evidence and do not fabricate canonical facts.
- Import upload validates size/extensions, stores a UUID storage key and preview; validate maps/coerces and records row errors/duplicates/FK checks; commit writes row-by-row and allows skipped errors. Bind signoff to source hash + mapping + edited values; stable row ID, idempotent retries, per-row result, transactional parent/child writes and reconciliation are needed.
- Tenant FK to Patient.id plus independent tenant FK does not prove equal tenant on both rows. Use tenant-composite keys/FKs or proven database policy, plus service authorization checks. Mock-based concurrency tests do not prove live DB isolation.

## Batch 18 — OpenEMR prescriptions, dispensing, service orders and document evidence
Sources include https://github.com/openemr/openemr/tree/master/Documentation/EHI_Export/docs/tables
- Prescriptions store patient, provider, pharmacy, encounter, start/end/filled dates, drug and RxNorm identifier, form/dosage/quantity/size/unit/route/frequency/interval/substitution/refills/per-refill, notes, active state, eRx source/upload and external IDs, indication and PRN. Template defaults, actual prescription, dispensing and drug sale must remain different concepts.
- Drug sales have transaction type sale/purchase/return/transfer/adjustment, patient/encounter/prescription/inventory links, quantity, fee, date and posted-to-accounting flag. Drug inventory contains lot/expiry/warehouse/distributor/source fields. Use movement ledger for stock, not only a current quantity.
- Procedure order header + normalized code lines + report + result are separate. Header includes provider/patient/encounter, collected/ordered/transmitted timestamps, priority/status, instructions, external lab control ID, lab, specimen type/site/volume/fasting, diagnosis, scheduled date/start/end, performer and facility. Report has collection/report timestamps with timezone, specimen number, status/review status and lab notes. Result has result type/value/unit/reference range/abnormal state/final/corrected status. Order, result and clinician review differ.
- Patient problem/allergy issues include coded diagnosis, dates, active state, verification, severity/reaction and eRx sync IDs; issue_encounter links problems to encounters/resolution. Immunizations include CVX/manufacturer/lot/expiry/amount+unit/route/site/actor/source/refusal.
- patient_reminders represent ongoing clinical due obligations by category/item/due status/active dates/channel flags, not a notification attempt. Documents include type, URL/thumbnail/MIME/size/pages/logical date/hash/owner/category, encounter/audit/encryption/DICOM action metadata/deleted and external polymorphic references. Onsite documents record patient signature and authorizing signature/status/time, review and denial reason.

## Batch 19 — DentalPin approval queue, tool registry, locking and plan/appointment state
Sources: https://github.com/dentalpin/dentalpin/tree/main/backend/app/core/agents ; https://github.com/dentalpin/dentalpin/tree/main/backend/tests ; https://github.com/dentalpin/dentalpin/blob/main/backend/tests/modules/agenda/test_appointment_checkin.py ; https://github.com/dentalpin/dentalpin/blob/main/backend/tests/modules/treatment_plan/test_plan_budget_lifecycle.py
- AgentApprovalQueue stores clinic/agent/session/tool/JSON arguments/reason/status/reviewer/time/notes. Approval and execution must remain distinct. Inspected decision code reads pending state then updates it, without row lock in the excerpt; race behavior should be tested before adoption.
- Tool allowlist and role/permission are separate controls. Tool schema parameters have type/UUID/date validation. Agent context includes tenant/user/permission and session identity. None-vs-empty allowlist semantics must be explicit.
- Module dependency tests ensure consumers declare dependencies before foreign-key use. Event bus subscribers receiving the same DB session can participate transactionally; subscriber errors can roll back the originating business operation. Non-DB handlers are logged separately. Use outbox/transaction boundary intentionally.
- Appointment status transitions have explicit edges and append-only history, including synthetic initial event. Transition performs locked refreshed read; in_treatment requires chair assignment. Cabinet assignment has its own history. Check-in QR token is signed/time-limited/origin-bound and repeat scan idempotent; source-specific time thresholds are not ClearFlow defaults.
- Plan/budget tests verify rejected quote reactivation creates a fresh quote and resend versions the budget. Keep plan status, quote version, acceptance evidence, appointment state and treatment completion separate.
- GDPR module models retention policies/legal holds and erasure requests; patient hard delete is avoided in the reviewed design. A data category with no active retention policy or no explicit erasure field mapping is retained. This is a design example; legal rules and retention periods must be jurisdiction-specific.

## Batch 20 — authoritative payments, gateway/refund lifecycle, credit notes and inventory ledger
Sources: https://github.com/dentalpin/dentalpin/tree/main/backend/app/modules/payments ; https://github.com/dentalpin/dentalpin/tree/main/backend/app/modules/payment_gateways ; https://github.com/dentalpin/dentalpin/tree/main/backend/app/modules/billing ; https://github.com/dentalpin/dentalpin/tree/main/backend/app/modules/inventory
- PaymentRequest is a pre-payment attempt, not a receipt. It records requested amount/currency/method/allocation input, provider order/payment references, checkout/status snapshots, expiry/failure/cancel/confirmation, idempotency and linked core payment set once on confirmation. Only confirmed provider payment creates core Payment. Duplicate webhooks/no-op terminal states, amount/currency mismatch checks and row locks matter.
- GatewayRefundRequest does not create core Refund until provider completion; completion must be idempotent. Failed provider initiation does not create a refund; maximum refundable amount includes already completed refunds. Provider attempt status and cash/refund ledger are different records.
- Core payment is gross positive Decimal money event; PaymentAllocation may target budget or on-account; allocations sum exactly to receipt; refund sum does not exceed receipt; idempotency key has a unique partial index. Invoice association lives in billing-owned bridge so payment module does not need to depend on billing. Events with DB session allow bridge updates in same transaction.
- Invoice number and series have DB uniqueness. Credit-note cap includes live drafts and rechecks at issue; issue-time party/price/tax are snapshotted. Invoice balances derive from allocations/refunds rather than arbitrary paid amount, while projections are recomputable.
- Inventory current stock has nonnegative DB CHECK; every change uses SELECT FOR UPDATE row lock and append-only stock movement in same transaction. Opening stock and absolute corrections are ledgered. Consumption has partial unique idempotency key per treatment reference and stock item. Treatment-consumable mapping defines stock quantities used per catalog treatment, but actual deduction happens only on performed event.
- Prescription lifecycle: draft -> issued -> cancelled. Issued records freeze; correction is controlled cancel/reissue, prescriber snapshot remains, only human prescriber issues; agents can draft only.

## Batch 21 — specialist dental records, images, recall and clinical AI review
Sources: https://github.com/dentalpin/dentalpin/tree/main/backend/app/modules/periodontogram ; https://github.com/dentalpin/dentalpin/tree/main/backend/app/modules/orthodontics ; https://github.com/dentalpin/dentalpin/tree/main/backend/app/modules/recalls ; https://github.com/dentalpin/dentalpin/tree/main/backend/app/modules/media ; https://github.com/dentalpin/dentalpin/tree/main/backend/app/modules/imaging_ai
- Periodontogram is a dated snapshot, with one draft per patient and immutable closed snapshots. Tooth rows have FDI number, presence/implant, mobility/prognosis, buccal/lingual furcation and keratinized-gingiva values; per-site rows cover up to six sites with probing depth, gingival margin, bleeding on probing, plaque and suppuration. Indices are computed when snapshot closes; the cached aggregates can be recomputed.
- Orthodontic case tracks appliance type (metal/esthetic/self-ligating brackets, aligners, functional, retention), lifecycle, start/estimated duration, diagnosis notes, upper/lower wire and plan link. Controls store performed time/actor, wires, procedures, other procedure text, aligner number, hygiene, notes, next-control weeks, appointment/session. Due date is derived from latest control and recall is upserted; case/control/action are distinct.
- Recall is a care obligation: due month/optional date, reason/reason note, priority/status, recommending/assigned professional, last contact time/count, linked appointment and treatment/category snapshot, completed time. RecallContactAttempt is append-only and includes actor, channel, outcome, time and note. Recall settings contain reason intervals/category map and auto-suggest/auto-link toggles. Recall row is not a send/delivery log.
- Media Document separates administrative document type from media kind/category/subtype, capture time, original filename, MIME/size, unique storage path, uploader/status, tags and bidirectional paired-document relation. Original image remains intact; derivatives are thumbnail/medium. EXIF timestamp is capture time, not upload time. Attachment owner registry validates polymorphic links; no FK on owner_id is an intentional modularity trade-off which needs service/test coverage.
- Imaging AI job records source document/series, backend, model ID/version, status, queue actor, review status/confirming clinician, runner log/errors and artifact document links. An autonomous agent proposes; clinician confirms; artifacts are drafts, not diagnoses. Background execution uses its own session and reaper handles stuck jobs.

## Batch 22 — migration provenance and imported clinical/financial history
Sources: https://github.com/dentalpin/dentalpin/tree/main/backend/app/modules/migration_import ; https://github.com/dentalpin/dentalpin/tree/main/backend/tests/modules/migration_import
- DPMF import package includes metadata, entity counts/schema versions, file manifest with canonical UUID/parent/path/size/SHA-256/MIME, warnings and per-entity payload + raw_source_data + extracted timestamp. ImportJob records source system/adapter/exporter/format version, tenant label, declared/computed integrity hash, entity counts/progress/checkpoint, fiscal compliance opt-in and start/completion/errors.
- EntityMapping is clinic-scoped idempotency key using source system + entity type + canonical source UUID and maps to destination table/ID. MappingDecision proposals separate exact/fuzzy links/create from operator accepted/relinked/create_new/ignored decision. External IDs are not FKs; resolver is authoritative. Operator choice beats fuzzy matcher output.
- Import job executes in a background task and resumes through checkpoints/entity mappings. Source tenant ID is never trusted; clinic comes from authenticated context. Source passphrase stays in memory; hash/version is checked. Fiscal/compliance data import is explicit opt-in and only if compatible module is installed.
- Critical accounting lesson: source receivable/debt records, not catalogue procedure price, are the source for historical patient-earned/receivable ledger. A performed treatment might be no-charge, family/staff, bundled or historically unbilled; import clinical care independently from financial debt. Skip cancelled, uncollectible, zero balance and unmapped debt rows with explicit warnings.
- Planned/performed treatment mapping prefers stable budget-line UUID when present; tariff/procedure ID can change between planning and completion. Fallback key may use patient/procedure/type/teeth/date window but should not silently pair uncertain twins. Keep an unmatched state for review.
- Source-inactive professionals referenced by historical appointments, treatments, plans and payments should be imported as inactive historical identities rather than deleted or promoted into new active schedule choices. Keep source role/activity and the deactivation decision.
- Module docs explicitly state no batch rollback in v1; partial results remain. ClearFlow needs explicit partial status, warning/row outcome, checkpoints, idempotent reruns, reconciliation and a recovery procedure. Do not report completion while unresolved entities/files/links remain.

## Cross-batch ClearFlow acceptance tests added to the backlog
1. Concurrent duplicate AI approval decisions; stale or consumed proposal rejection; approval hash/version mismatch.
2. Real database race tests for claim/receipt posting, invoice numbering, credit note limit, payment idempotency and stock consumption.
3. Cross-tenant FKs/owner registry validation for patient, payer, lab, documents, inventory and AI jobs.
4. Notification DNC/type opt-out/channel opt-out survives forced/manual send; only clinic automation toggle is bypassed; retries don't duplicate; concurrent dispatcher locks one message.
5. Eligibility staleness, benefit response versioning, multi-line remittance posting, reversal and secondary payer allocation.
6. Recall obligation does not imply message delivery; provider sent/delivered/read events are separate; template/provider/channel changes do not rewrite historical delivery evidence.
7. Periodontal closed snapshot immutability, orthodontic control timeline, AI imaging artifact remains draft until authorized clinician confirmation, media pairing same-patient validation.
8. Import source hash/mapping/row idempotency, resume after partial failure, unmatched clinical entity and opening-balance reconciliation.
