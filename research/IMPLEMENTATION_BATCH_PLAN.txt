CLEARFLOW DENTAL CLINIC — MASTER IMPLEMENTATION BATCH PLAN
Repository: clearflowint/clearflowdental
Branch: main
Status: PLANNING BASELINE — no implementation batch is marked complete by this document.
Purpose: Convert the existing research into a staged, testable, tenant-safe implementation. Research files remain the evidence/source-of-truth set; this plan is the execution sequence.

GOVERNING RULES
1. Read and reconcile the existing research before implementing a feature. Key inputs include PROJECT_NOTES.md and its addenda, RESEARCH_INDEX.md, RESEARCH_COMPLETION_STATUS.md, SOURCE_COVERAGE_REGISTER.md, SOURCE_FIELD_MAPS.md, FIELD_LEVEL_INVENTORY.md, TRACEABILITY_MATRIX.md, CROSS_SYSTEM_COMPARISON.md, IMPLEMENTATION_GAP_REVIEW.md, and CONVERSATION_DECISION_LOG.md.
2. Do not treat research documents as executable functions. Build actual frontend, backend/workflow assets, and tests from the approved requirements.
3. Security and privacy are release gates, not later polish. Every read, create, update, deactivate, delete, export, background job, and cross-entity lookup must enforce authenticated tenant scope server-side.
4. No clinical write, signature, prescription issuance, medication dispensing, or destructive action may be performed by AI without an explicit, informed user confirmation. AI can assist with retrieval/drafting only within the permissions and audit rules approved for that workflow.
5. Use deterministic Python for supported business rules and validation wherever practical. Use AI only when a language/interpretation task genuinely requires it. Do not trust AI output as validated clinical truth.
6. Never put admin/API secrets in the frontend, Git, logs, prompts, or client-visible errors. Do not sync secrets or resources from GitHub to Windmill.
7. Keep source, schema, migrations, tests, deployment configuration, and operator documentation versioned. Prefer small, reversible changes with explicit acceptance criteria.
8. No claim of live deployment or end-to-end verification without a recorded test result from the actual target environment.

BATCH 01 — PRODUCT SCOPE, USERS, AND CLINICAL GOVERNANCE
Goal: Agree on the first usable release and its authority boundaries.
Work:
- Define clinic/tenant, locations, users, roles, permissions, and supported user journeys.

- Define patient consent, correction/amendment, record retention, export, audit, emergency access, and account offboarding policies for review.
- Identify jurisdiction-specific regulatory requirements and obtain qualified clinical/legal review where required.
- Define which features are explicitly excluded from the first release.
Acceptance:
- Scope and role matrix reviewed.
- Each clinical workflow has an accountable human role and approval point.
- Open regulatory decisions are tracked, not guessed.

BATCH 02 — THREAT MODEL AND TENANT-ISOLATION SPECIFICATION
Goal: Make tenant isolation and authorization testable before feature implementation.
Work:
- Document trust boundaries, actors, assets, attack paths, and sensitive-data flows.
- Define server-side authorization policy for every resource and operation.
- Prevent tenant IDs supplied by clients from being treated as proof of access.
- Define least-privilege service identities, secret handling, session expiry/revocation, rate limits, and safe error behavior.
- Define two-tenant negative tests for direct IDs, nested references, search, exports, attachments, background jobs, and indirect lookups.
Acceptance:
- Threat model and access-control matrix reviewed.
- Every planned endpoint/job has an authorization rule.
- Cross-tenant test cases exist before the corresponding endpoint is accepted.

- Define dev/test/staging/production configuration boundaries.

BATCH 04 — APPWRITE BACKEND FOUNDATION AND AUTHENTICATION

BATCH 05 — DATA MODEL, SCHEMA CONTRACTS, AND MIGRATION POLICY

Acceptance:

BATCH 06 — SERVER-SIDE ACCESS LAYER AND TENANT-BOUND OPERATIONS
Goal: Centralize authorization and validated data access.
Work:
- Implement reusable server-side helpers for identity, tenant membership, role checks, input validation, and tenant-scoped retrieval.
- Require tenant-scoped authorization on every mutation and read; avoid insecure direct object references.
- Enforce ownership checks on related records and nested resources.
- Add idempotency and concurrency controls for retryable writes where required.
- Ensure errors do not reveal whether another tenant's records exist.
Acceptance:
- Automated negative tests cover read, create, update, deactivate, delete, search, export, and nested references across two tenants.
- No route or job can bypass the access layer without an explicit, reviewed exception.
- Audit records are generated for security-sensitive operations.

BATCH 07 — FRONTEND SHELL AND AUTHENTICATED MOBILE UX
Goal: Create the responsive clinic application shell after the backend contract is stable.
Work:
- Build the mobile-first responsive frontend and navigation using the agreed framework and repository conventions.
- Implement loading, empty, validation, offline/network-error, expired-session, and permission-denied states.
- Use server-returned records as the source of truth; frontend calculations must not become authoritative clinical or financial logic.
- Prevent stale tenant data from leaking across logout/login or tenant switching.
Acceptance:
- No horizontal scrolling at target mobile widths.
- Session transitions clear tenant-specific client state.

BATCH 12 — MEDICATIONS, PRESCRIPTIONS, AND DISPENSING SAFEGUARDS

- Prevent AI from issuing prescriptions or dispensing medication autonomously.
Acceptance:
- Negative tests cover missing authorization, invalid fields, allergy conflicts, duplicate issuance, cancellation, and tenant crossing.

Acceptance:
- Reconciliation and concurrency tests pass.

Acceptance:

BATCH 17 — NOTIFICATIONS AND BACKGROUND AUTOMATION
Goal: Add dependable reminders and background jobs.
Work:
- Define job payload contracts, tenant identity, idempotency keys, retry/backoff, dead-letter/manual-recovery process, and delivery audit.
- Keep secrets in platform secret stores; never sync them from the repository.
- Ensure jobs re-check tenant authorization and record state at execution time instead of trusting stale payloads.
- Keep notification content minimal and avoid exposing clinical details on insecure channels.
Acceptance:

BATCH 18 — AI ASSISTANCE AND NATURAL-LANGUAGE EXECUTION GUARDRAILS
Goal: Add AI only where it materially improves language-based tasks.
Work:

- Treat AI outputs as untrusted proposals; validate against deterministic schemas and approved business rules.
- Separate read-only assistance, draft creation, and consequential actions.
- Require explicit user review/confirmation before clinical writes, signature, prescription issuance, dispensing, destructive changes, or external communication when applicable.
- Log model/version, request purpose, source references, human approval, and final action without retaining unnecessary sensitive prompts.
Acceptance:
- AI cannot directly bypass authorization or call unrestricted mutation tools.
- Invalid, hallucinated, cross-tenant, and prompt-injection test cases fail safely.
- AI functionality can be disabled without breaking deterministic core workflows.

CROSS-BATCH RELEASE BLOCKERS
- Any confirmed cross-tenant data exposure or mutation.
- Any unauthenticated or unauthorized access to protected patient data.
- Any AI-triggered consequential action without required human approval.
- Any prescription, dispensing, signature, or clinical rule lacking required source validation and qualified review.
- Any migration or deployment without a tested recovery path where data loss is possible.
- Any claim of compliance or clinical safety unsupported by current evidence and qualified review.
